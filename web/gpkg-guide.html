MAINTENANCE MANUAL · GEOPACKAGE BUNDLES FOR NOVICE GIS TECHNICIANS

One file holds
the whole project.

Every .gpkg handed to you here is not just data — it is a self-contained bundle carrying the project, its layers, its styles, and its print layouts in one SQLite file. This manual explains how that bundle is put together, how to feed it new data safely, what quietly breaks the styling when you do, and how to fix it when it happens.

Format OGC GeoPackage (SQLite) Contains project · layers · styles · layouts Audience First maintenance pass, no assumed QGIS depth
01

Summary

The 90-second version

A normal GIS handover gives you a pile of separate files: a .shp here, a .qml style there, a .qgz project pointing at both by file path. Move any one of them and the project opens with red exclamation marks and grey layers. These bundles are built to avoid exactly that. Everything — the vector and raster layers, the QGIS project definition, the saved layer styles, and any print layouts — lives inside one .gpkg file, in dedicated internal tables the GeoPackage spec and QGIS both understand natively.

That means the bundle is portable: copy the single file to a new machine, open it, and every layer still finds its style and every layout still finds its map frame — because nothing points outside the file. It also means the bundle is fragile in a specific, predictable way: because everything is addressed by name inside one file, renaming a table, changing a field, or reprojecting a layer inside that same file is enough to sever a link that used to be automatic.

Three things to internalize before touching anything

  1. The style lives with the data, not with QGIS. Styles saved "to the layer" are rows in the GeoPackage's own layer_styles table, keyed to the layer's table name. They travel with the file. They are not a QGIS preference and will not survive on a different machine unless they are actually inside the .gpkg.
  2. The project references layers by table name, not by row order or column position. As long as a replacement table keeps the same name and the same field names, the project usually reopens clean. Rename a table or a key field and the link breaks even though the geometry is perfectly valid.
  3. "Updating the data" and "replacing the file" are different operations with different risk. Loading new rows into an existing table preserves every link. Swapping in a whole new .gpkg, or importing a fresh shapefile over an existing layer, is where things go wrong — covered in full in §5.
Read §2 (Bundle Anatomy) and §3 (First Open) once before doing any update, even a routine one. Everything after that is procedure you'll return to as reference.
02

Bundle Anatomy

What's actually inside the file

A GeoPackage is a single SQLite database with a .gpkg extension. Everything below is a table or a row inside that one database — there is no separate folder, no sidecar file, and (for the parts covered here) nothing to keep in sync by hand.

Part of the bundle Where it actually lives Keyed by What breaks it
Layers (vector tables, raster tiles) Standard GeoPackage feature/tile tables, one per layer Table name Renaming, deleting, or dropping and recreating the table under a new schema
Project A QGIS Projects table, holding the saved .qgz/.qgs project XML as a blob inside the same file (when the project was saved into the GeoPackage rather than as a separate file) Project name Saving the project to a separate .qgz instead — which silently forks the project from the bundle
Styles layer_styles table — one row per saved style, storing the QML/SLD definition as text f_table_name (must match the layer's table name exactly) + a useAsDefault flag Renaming the layer table without updating f_table_name; deleting and recreating the layer under the same visible name but a different internal table
Layouts Embedded inside the project blob, as <Layout> elements referencing each map item's layer set by ID Layer ID (an internal QGIS ID, not the table name) Removing a layer and adding a "new" one with the same name — the map item in the layout keeps pointing at the old, now-missing layer ID

Why the project stores styles this way

When a layer is added from a GeoPackage table, QGIS can load its style straight from that layer's row in layer_styles instead of from the project file. Saving a style with Layer Properties → Symbology → Style → Save Style… → Save in database (GeoPackage) writes it there. This is what makes the style survive a fresh Add Layer even in a brand-new project — the style isn't remembered by QGIS, it's read off the layer itself.

Why this differs from a folder of shapefiles

A .shp + a hand-saved .qml next to it is two files connected only by the project remembering a file path. Move the shapefile, and the .qml is orphaned even though nothing about the data changed. A GeoPackage collapses that link into rows in one database, so "moving the data" and "moving the style" become the same action by construction.

Confirm what a specific bundle actually contains before assuming. Not every .gpkg handed to you will have an embedded project or layouts — some are data-only. Open it in DB Browser for SQLite (§3.2) and check for a QGIS Projects table before assuming a project is inside.
03

First Open — Orientation Pass

Before you change anything

3.1 Open the project the right way

If the bundle carries an embedded project, open it with QGIS → Project → Open From → GeoPackage… and pick the project row, not by dragging the .gpkg onto the canvas — dragging it in only adds the layers as a flat list, without the layer tree groups, layouts, or saved map canvas extent the project defines.

Once open, check the Layers panel against the Layout manager (Project → Layouts…) before touching data: note every layer name, and every layout's map item and its layer set. This is your baseline — if a style or a layout breaks later, you'll know exactly what it looked like before.

3.2 Inspect the bundle outside QGIS

Use DB Browser for SQLite (free, cross-platform) to look inside the .gpkg directly. Two tables matter most for maintenance:

  • gpkg_contents — the authoritative list of every table the GeoPackage considers a layer, with its geometry type and bounding box. This is the ground truth if QGIS shows a layer as broken.
  • layer_styles — every saved style, and which layer (f_table_name) each one is attached to. If a layer lost its style, this is the first place to look — either the row is gone, or f_table_name no longer matches any table in gpkg_contents.

Read-only by default: browse and note what you find, but don't edit rows directly in DB Browser unless a repair recipe in §7 says to — QGIS is the safer tool for anything that touches geometry or styling, because it validates as it writes.

Make a dated copy of the .gpkg before your first edit of any kind (see §8). A file this self-contained is also a file where one bad save touches everything at once.
04

Using the Same Project with Newer Data

The core workflow, ranked safest first

"New data" usually means one of three things, and they carry very different risk. Pick the narrowest one that actually fits the update you're doing.

4.1 Append or refresh rows in place lowest risk

When to use it
The schema (field names and types) hasn't changed — you're adding new records, updating attribute values, or replacing the season/month of survey points, but the table structure is the same.
How
In QGIS, open the target layer's attribute table and use field calculator / paste features, or import the new rows with Layer → Add Layer → Add Vector Layer pointed at the source, then copy features → paste into the existing layer. The table name and every style reference stay untouched because you never dropped the table.
Why it's safe
Nothing about the layer's identity (table name, field names) changes, so layer_styles and any layout map item referencing it keep working without any action from you.

4.2 Overwrite a layer's contents, same schema moderate risk

When to use it
A full new dataset for the same theme — this quarter's parcel boundaries replacing last quarter's — where the field names and geometry type match the old layer exactly.
How
Use Database → DB Manager → Import Layer/File… and import into the existing table, with "Overwrite" ticked and the table name typed to match the current one exactly — case included. Do not use "Create new table" and then delete the old one; that generates a new internal table even if you give it the old visible name, which is exactly the failure mode in §5.1.
Verify
After import, reopen the project fresh (close and reopen, don't just refresh) and confirm the layer still carries its style automatically and any layout map item still shows it. If it doesn't, go to §8.1 before doing anything else.

4.3 Swap in a whole new .gpkg bundle highest risk

When to use it
You've been handed a brand-new bundle — new source, new export — meant to replace the current one wholesale, not just refresh a layer inside it.
How
  1. Open the new file's own embedded project if it has one — don't try to force the old project onto the new file. Check whether the new bundle already carries its own styles and layouts before assuming you need to redo anything.
  2. If the new bundle is data-only and needs the old project's styling: open the old project, and for each layer use Layer Properties → Symbology → Style → Load Style…, pointed at the corresponding table's saved style — either from the old .gpkg's layer_styles or from a style export (see §8.2).
  3. Re-point each layout's map item at the new layer via the Layers panel inside the Layout item properties, then re-check every map frame's extent — a new dataset can have a different bounding box than the old one, leaving a layout that renders but frames the wrong area.
Why it's risky
Everything that made the old bundle self-contained — style bindings, layout layer references — is scoped to the old file. A new file starts that binding over from nothing unless you deliberately carry it across.
Rule of thumb: if you can get away with §4.1 or §4.2, do that instead of §4.3. Every step in §4.3 is a place styling or layouts can silently fall out of sync, and it is the workflow responsible for most of the breakage in §5.
05

How Styling Actually Links to Data

The mechanism, not just the symptom

QGIS doesn't remember "this layer is red" as a fact about the project. It resolves style at layer-load time, by looking for a row in the GeoPackage's layer_styles table where f_table_name matches the layer's actual table name, and where useAsDefault is set to true for that table. If it finds one, it applies it; if it doesn't, the layer loads with QGIS's random default symbology.

This is why a style can vanish with the geometry completely intact: the geometry table and the style row are two separate rows in two separate tables, connected only by a name string. Nothing enforces that the name string stays correct when either side changes independently.

Field mappings inside a style

A saved style can reference specific attribute field names directly — a categorized renderer keyed on a land_use column, a data-defined label expression reading site_name, a rule-based renderer testing status = 'active'. These field names are baked into the style definition text itself, not re-derived from the table at load time.

Layout map items

A layout's map frame doesn't store "the parcels layer" as a name — it stores the internal QGIS layer ID assigned when that layer was added to the project. Deleting a layer and re-adding "the same" layer, even under an identical visible name, mints a new ID, and the layout frame is left pointing at nothing.

Keep this mental model: style rides on table name. Field-driven symbology rides on field names. Layout frames ride on layer ID, not name at all. Each is a different string or ID, matched independently — which is exactly why a change can break one and leave the other two intact.
06

Layouts & Atlases

Print layouts embedded in the bundle

Layouts live inside the same project blob as everything else — there is no separate .qpt file to lose track of as long as the project itself stays inside the GeoPackage. Each map item on a layout holds its own extent, scale (locked or following the canvas), and layer set.

6.1 Locked vs. dynamic extents

Check whether each map item's extent is locked (a fixed bounding box, set once) or set to follow the main canvas. A locked extent is invisible to a data swap — it will keep framing the old area even after the underlying data has moved or grown, silently cropping the new dataset out of the printed page. This is a common, quiet failure after §4.3: the layout still "works," it's just wrong.

6.2 Atlases

If a layout drives an atlas (one page per feature — one page per parcel, one page per survey site), the atlas's coverage layer is itself a layer reference subject to the same layer-ID binding as any map item. Swapping the coverage layer's underlying table (§4.2) is safe as long as the table name is unchanged; deleting and re-adding it (§4.3 without care) breaks the atlas the same way it breaks a static map frame.

After any data update, open every layout in the manager, not just the ones you expect to be affected — an atlas coverage layer is easy to forget because it isn't visible on the main canvas.

What Breaks Styles — Failure Reference

Cause, symptom, and why it happens
Cause Symptom you'll see Why
Renaming a layer's table during import ("create new table" instead of overwrite) Layer loads with random default symbology; layout frame goes blank or shows "Layer not found" f_table_name in layer_styles and the layer ID in the layout no longer match anything
Renaming or removing a field referenced by a categorized/graduated renderer or a label expression Symbology renders as a single flat color or a fallback ("all others") category; labels disappear or show an expression error The style's renderer definition references the old field name literally; it doesn't fail loudly, it just can't classify anything
Changing a layer's geometry type (e.g. Polygon → MultiPolygon, or Point → MultiPoint) during re-import Layer imports but symbol renders differently or not at all; some renderer types are geometry-type specific Simple vs. multi- geometry types are technically distinct in a GeoPackage; a style built for one doesn't always carry cleanly to the other
Reprojecting a layer to a different CRS on import Layer appears in the wrong place, or not within the map canvas extent at all; layout map item appears empty Geometry stores its own CRS per GeoPackage layer; a mismatched CRS against the project's other layers or the layout's locked extent puts data outside the visible frame
Saving the project as a separate .qgz "just to be safe," then continuing to edit the .gpkg's data The .qgz and the .gpkg drift apart; opening one or the other shows different states The project fork is now tracking its own copy, not the bundle's embedded project — the two are no longer the same object
Deleting and re-adding "the same" layer instead of overwriting in place Style is gone even though the table name looks unchanged; layouts referencing it go blank A new internal layer ID is minted on add, even under an identical display name — layout bindings follow ID, not name
Editing the .gpkg with two applications open at once (e.g. QGIS and DB Browser both writing) SQLite database lock errors, or a corrupted/partially-written file on next open GeoPackage is a single SQLite file; concurrent writers without WAL-safe handling can corrupt it
The common thread: every failure above changes a name, an ID, or a type while the surrounding link (style row, layout frame, renderer field) keeps pointing at the old value. Nothing here is data corruption — it's a broken pointer, and every one of them is fixable in §8 without redrawing anything from scratch.
08

Repair Recipes

Fixes, in the order to try them

8.1 A layer lost its style but the table name is unchanged

  1. Right-click the layer → Properties → Symbology → Style → Load Style…
  2. Choose "From datasource database (GeoPackage)" if a saved style still exists in layer_styles for that table — check with DB Browser (§3.2) first if unsure.
  3. If no matching row exists, load from a style export instead (see §8.2 on keeping .qml backups) — then re-save it to the database with Save Style… → Save in database so it's bundled back into the .gpkg for next time.

8.2 Categorized/graduated symbology fell back to one flat color

  1. Open Symbology and check the Value / Column dropdown for the renderer — if it shows a field name struck through or blank, the field it was built on no longer exists under that name.
  2. Re-point it at the new field name, then use Classify to rebuild the category/graduated breaks — the color ramp and style settings are preserved, only the field binding needs redoing.
  3. If labels also broke, open Layer Properties → Labels and fix the field reference in the same way, or in the label expression if it's expression-driven.

8.3 A layout map item is blank or missing its layer

  1. Select the map item → Item Properties → Layers → untick "Follow map theme" if needed, then manually re-check the correct current layer in the list.
  2. If the extent is locked to the old data's bounding box, click Set Layer Extent (or manually zoom-and-set) to reframe it against the new data.
  3. For an atlas, reopen Layout → Atlas settings and re-select the coverage layer the same way.

8.4 The project and the GeoPackage have drifted apart

  1. Confirm which is authoritative — usually the embedded project inside the .gpkg, unless the team has explicitly moved to a standalone .qgz.
  2. If the standalone .qgz has newer edits worth keeping, re-save it back into the GeoPackage with Project → Save As → GeoPackage, overwriting the embedded copy.
  3. Going forward, pick one home for the project and don't "Save As" a second copy out of caution — that caution is what causes the drift. Use §8 (backups) instead.

8.5 SQLite lock error or a file that won't open

  1. Close every application that has the file open — QGIS, DB Browser, a second QGIS instance — and try again.
  2. If it still won't open, work from your last dated backup (§8) rather than attempting SQLite repair tools on a file that may be corrupted; on a small municipal-scale bundle, restoring from backup is faster and safer than debugging a database file.
If a recipe above doesn't resolve it, stop and restore from backup before trying a second, more invasive fix — stacking uncertain repairs on top of each other is how a recoverable problem becomes an unrecoverable one.
09

Geometry & CRS Pitfalls

The failures that look like styling bugs but aren't

Some of what looks like a broken style is actually a geometry or projection mismatch presenting the same way — nothing draws, or it draws in the wrong place. Rule these out before assuming the style itself is at fault.

Check the CRS first

Right-click the layer → Properties → Information and confirm the CRS matches the rest of the project. A layer imported straight from a source in a different CRS than the project's will still load — QGIS reprojects on the fly — but a layout item with a locked extent defined in the project's CRS can end up framing empty space if the new layer's real-world footprint shifted.

Check for invalid or empty geometry

Use Vector → Geometry Tools → Check Validity after any import from an external source. A handful of self-intersecting polygons from a messy source file can render as gaps in an otherwise-correct-looking layer, which is easy to mistake for a symbology problem.

Diagnostic order that saves time: CRS → validity → styling. Confirming the first two takes under a minute each and rules out the two failure modes most often mistaken for a broken style.

Backups & Versioning

Cheap insurance against a self-contained file

8.1 Before every update

Copy the whole .gpkg to a dated filename before touching it — e.g. parcels_2026-08-19.gpkg — even for a routine data refresh. Because everything lives in one file, there is no "just the data" or "just the layout" to revert independently; the backup is the only undo you'll have once a save has gone through.

8.2 Export styles as a safety net, separately from the bundle

For any layer with a style worth protecting, also export it as a standalone .qml via Save Style… → Save to file, kept alongside your backups. This costs a minute and means a style can always be reloaded (§8.1) even in the worst case where the bundle's layer_styles table itself is damaged.

8.3 Version-control the file the way it deserves

A .gpkg is a binary SQLite file — regular version control tools will store a full new copy on every change rather than a meaningful diff. Dated copies in a clearly named folder, or a dedicated large-file tool if your team already uses one, both beat relying on a generic git history to tell you what changed inside the file.

Backups are the difference between "an afternoon's rework" and "redo the styling from scratch." Every recipe in §8 assumes one exists.
11

Update Checklist

Run this every time, top to bottom
  1. Back up. Dated copy of the .gpkg, per §8.1.
  2. Note the baseline. Layer names, field names, geometry types, and every layout's map items — per §3.1.
  3. Pick the narrowest workflow that fits. Append (§4.1) before overwrite (§4.2) before full bundle swap (§4.3).
  4. Preserve names on the way in. Same table name, same field names, same geometry type unless you have a specific reason to change them — and if you do change one, expect to redo the matching link in §7.
  5. Reopen the project fresh (not just refresh) and check every layer's symbology against the baseline from step 2.
  6. Open every layout, not just the ones you expect to be affected, and check extents against the new data's real footprint.
  7. Check the CRS and geometry validity of anything newly imported, per §9, before blaming styling for a blank layer.
  8. Re-save the style to the database if you had to reload it from a .qml backup, so the bundle stays self-contained for the next person.
  9. Keep the project's home singular. Don't leave a stray .qgz fork sitting next to the bundle — per §8.4.
A clean update run touches steps 1–6 and nothing else. If you find yourself in §7 (Repair Recipes), that's a sign one of steps 3–4 was skipped or a rename slipped through — worth a mental note for next time, not a cause for alarm.

Glossary

Terms used throughout this manual
GeoPackage (.gpkg)
An OGC open standard storing vector layers, raster tiles, and optionally a QGIS project, all as tables inside one SQLite database file.
Bundle
This manual's term for a .gpkg that carries not just data but an embedded project, styles, and layouts together — the pattern every file here follows.
layer_styles
The internal GeoPackage table QGIS reads from and writes to when a style is saved "to the database" — one row per style, matched to a layer by table name.
gpkg_contents
The internal table listing every layer the GeoPackage format recognizes, with its geometry type and extent — the ground-truth list to check when QGIS's own display looks wrong.
Layer ID
An internal identifier QGIS assigns when a layer is added to a project — not the same as the layer's display name or its table name. Layout map items bind to this ID.
Locked extent
A layout map item's bounding box set to a fixed value rather than following the live canvas — stable for print, but blind to a dataset's footprint changing underneath it.
Coverage layer
The layer an atlas iterates over, generating one output page per feature — subject to the same layer-ID binding as a static map item.
