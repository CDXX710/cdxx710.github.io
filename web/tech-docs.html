A prototype read end to end.

01

Executive Summary

The 90-second version

Caribbean Archives is a browser-only geospatial research tool for exploring a corpus of historical Caribbean documents — letters, reports, bibles, poems, novels, field notes — classified by date, document type, author type, and their relationship to creole languages ("written in creole" / "about creoles" / unknown). It is published as a GitHub Pages site; index.html is a link index that labels the map as a prototype, and the map's own header reads "Illustrative data only."

The map experience is not a "pins on a map" viewer. It is a spatial query and analysis surface. The user draws rectangles, ellipses, lassoes, or polygons over the map — or clicks an island boundary directly — and combines those hits with boolean set algebra (new / union / subtract / intersect, with Shift/Alt/Ctrl as temporary modifiers). The resulting selection drives a results list, an analytics panel that recomputes distributions live, and an export dialog. Meanwhile a footer year-range slider, a legend of per-category toggles, and a clickable decade histogram all filter the same dataset from different directions, and every one of those interactions is mirrored into the URL as a shareable, Back/Forward-navigable link.

Technically, it is 36 hand-written ES modules (~5,400 LOC) plus ~4,000 LOC of plain CSS, with no build step, no bundler, no package.json, and no dependency manifest of any kind. Leaflet 1.9.4 is pulled from a CDN; noUiSlider and topojson-client are vendored as local files. Modules are IIFE-closure singletons (const X = (() => { ... })()) exported by default and wired together through a 12-line event bus that is the only channel modules use to talk to each other. There is no framework, no store library, and — verified by search — zero fetch, XMLHttpRequest, or localStorage calls anywhere in the application. State lives in memory and in window.history.

This architecture is a good fit for what the project is. The absence of a build step means the deployed artifact is the source; the absence of a framework means Leaflet's DOM is directly addressable (selected markers are styled by toggling a CSS class on Leaflet's own divIcon element); and the event bus keeps 36 modules decoupled without ceremony. The code is unusually well commented — comments explain why, and several record rejected alternatives, which is rare and valuable.

Three structural facts dominate everything downstream

  1. Records have no identity. Selection, and the shareable URL, use array indices into ArchiveData.features. The code flags this itself in state-sync-manager.js.
  2. The map is a singleton by construction. MapCore calls L.map("map") at module evaluation time; ~15 modules import and use MapCore.map directly. There is no second map without a refactor.
  3. StateSyncManager is already two-thirds of a story engine. It defines a canonical serializable application state, a function to read it from the live app, and a function to apply it back. A story step is that object plus narrative text.
The highest-value near-term work is small, product-neutral, and unblocks both future modes: give records stable IDs, add a batched filter-apply API, and extract the state-application logic that is currently private inside StateSyncManager.

Project Context and Purpose

What's real, what's simulated

2.1 What is real

Everything about the interaction model is real and fully implemented. The drawing tools, the boolean selection algebra, the modifier-key overrides, the point-in-polygon hit testing, the dual-resolution boundary simplification, the URL state sync, the light/dark theming, the responsive bottom-sheet layout, the custom popup positioning — all of it is genuine, working code, not a mockup.

The geographic data is also real: js/map/data/boundaries-topo.js is a 370 KB TopoJSON file of Caribbean administrative and maritime boundaries carrying GADM-style properties (NAME_0, GID_0, TYPE, FLAG), and img/tiles/ contains 4,519 pre-rendered raster tiles (211 MB, zoom levels 4–10) for two historical map overlays. The repository is 415 MB, and almost all of that is imagery.

2.2 What is simulated

Three things, and the boundaries are clean:

Area Reality
The archive dataset 25 features hardcoded as a GeoJSON literal in archive-data.js. Every abstract is the same LOREM constant; thumbnails cycle through 12 reused JFIF files.
Export ExportDialog offers 13 formats (PNG, SVG, PDF, GeoJSON, Shapefile, GeoPackage, FlatGeobuf…). The Export button's handler is close(). It is a fidelity mock of a real export UI, with no encoder behind it.
Source-text viewer VisualizerModal renders a static HTML blob from visualizer-content.js, triggered through a global window.toggleWindowPopup referenced by an inline onclick in the popup markup.

2.3 Why it reads as finished

The prototype clears the usual "demo" bar because it invested in the parts demos normally skip: keyboard access on markers (role="button", tabindex, Enter/Space), aria-pressed / aria-expanded maintained on every toggle, focus return on Escape-dismiss, a documented mobile breakpoint, prefers-color-scheme as the default theme source, and shareable deep links. The visual system is a coherent token set (--color-cat-*, --color-writ-*, --color-role-*, fluid clamp() sizing) rather than ad-hoc values.

The right way to read this: the product hypothesis being tested is the interaction design, not the data pipeline. Mock data is sufficient — arguably necessary — for that test. Hardcoding 25 records is a deliberate scope decision, not an omission.

High-Level Architecture

Layered by import direction, not by tooling

The project has a genuine layered architecture, enforced by import direction rather than by tooling. Lower layers never import upward.

Two properties are worth naming because they shape every future change:

State is federated, not centralized. There is no store. FilterState owns year range + three filter dimensions. SelectionState owns a Set of indices + the combine mode. ResultsViewState owns the "viewport vs. selection" toggle and sort. Basemaps owns the active layer IDs. Boundaries owns layer visibility. Each is authoritative for its slice and broadcasts changes. StateSyncManager is the only module that assembles a whole-application snapshot — and it does so by reading from each owner, not by owning anything itself.

Rendering is subscription-driven, not orchestrated. Nothing calls "render the app." Each panel subscribes to the events it cares about and re-renders its own subtree. AnalyticsPanel listens to filters:changed, selection:changed, and Leaflet's moveend; Markers listens to filters:changed, selection:changed, and search:queryChanged; they never reference each other.

Project Structure

Organized by responsibility, not file type

Four HTML pages sit at the top: index.html (a link index), and under web/, map.html (the subject of this report), data-sources.html (a GIS open-data reference), and css-cheatsheet.html (a design-token reference). The latter two are standalone documentation pages unrelated to the map's runtime.

The map's JavaScript is organized by responsibility, not by file type, and the directory names are meaningful:

  • js/map/data/ — the dataset, the boundary topology, and the decode/lookup layer over them. No behavior beyond caching.
  • js/map/state/ — pure state owners and pure logic. filter-state.js is explicit that there is no DOM here. state-sync-schema.js opens by declaring itself pure and unit-testable in isolation.
  • js/map/map/ — everything that touches Leaflet: the map instance, tile layers, boundary rendering, the rubber-band draw overlay, the zoom control.
  • js/map/markers/ — marker lifecycle, SVG icon generation (shapes.js, 20 KB of hand-authored icon paths for 7 categories × 7 author types × 3 roles), popup positioning, popup content.
  • js/map/ui/ — the floating panels and dialogs. Each panel module owns one panel and nothing else.
  • js/vendor/ — noUiSlider and topojson-client.

CSS mirrors this one-to-one: css/map/legend-panel.css ↔ js/map/ui/legend-panel.js ↔ #legend-panel in map.html. That three-way correspondence holds across every panel and is one of the strongest maintainability properties in the codebase.

Two dead files, both actively misleading. js/map/state/time-slider-algebra.js is a byte-identical copy of noUiSlider (verified by MD5 against js/vendor/nouislider.js) — 35 KB of minified vendor code filed under state/ with a name suggesting it contains the project's own time-range logic. js/map/data/topojson.js likewise duplicates js/vendor/topojson.js. Neither is imported or referenced anywhere. An engineer opening state/time-slider-algebra.js expecting domain logic will find a minified third-party bundle. Delete both.

Map System Deep Dive

Init order, boundaries, markers, selection

6.1 Initialization

map.html loads dependencies in a specific and load-bearing order: Leaflet's CSS and the vendored globals (noUiSlider, topojson) in <head>; then at the end of <body>, Leaflet's JS, then boundaries-topo.js (a classic script assigning BoundariesTopoFine / BoundariesTopoCoarse to window), then <script type="module" src="../js/map/app.js">. Because module scripts are deferred, L and the boundary globals are guaranteed present before any module evaluates.

app.js is 40 lines and does exactly one thing — bootstrap() — with two ordering constraints spelled out in comments:

mapTheme.init()        // must subscribe BEFORE Basemaps.init() calls setBase(),
Basemaps.init()        // because that first call sets the initial [data-theme]
Boundaries.init()
VisualizerModal.init()
Markers.init(ArchiveData.features)
Legend.init()
TimeSlider.init()
SelectionToolbar.init()
SelectionResults.init()
Searchbar.init()
AnalyticsPanel.init()
// dropdowns…
StateSyncManager.initialize()   // must run LAST: reads every module's freshly
                                // initialized state to compute "defaults",
                                // then may immediately override it from the URL

A subtlety that matters for §13: the Leaflet map is not created in MapCore.init(). There is no such function. map-core.js calls L.map("map", {...}) at module top level, inside the IIFE. Importing MapCore — which basemaps, boundaries, markers, draw-overlay, marker-popup, results-row, results-panel, analytics-panel, viewport-query, selection-toolbar, legend-panel, and state-sync-manager all do — instantiates the map as a side effect. It is a singleton by construction, not by convention.

Initial state resolution runs in three stages:

  1. Config supplies center [15.5, -61.2] (Dominica), zoom 8, and — notably — defaultBaseLayerId is computed at config-evaluation time from window.matchMedia("(prefers-color-scheme: light)"), so the map honours OS theme before any user input.
  2. Each module initializes to its own defaults: all filters on, no selection, year range = the dataset's full extent (Math.min/max over every feature's time).
  3. StateSyncManager.initialize() snapshots that as defaults, then calls hydrateFromCurrentLocation(). If a query string is present it is deserialized, sanitized against live bounds, and applied; otherwise defaults are applied unchanged. Either way it finishes with writeHistory("replace") so the very first history entry is well-formed.

6.2 The boundary layer

BoundaryData decodes TopoJSON to GeoJSON features and caches the result per simplification level in a module-level Map. Two levels exist — BoundariesTopoFine (~19% of source points) and BoundariesTopoCoarse (~7%) — and the file header records the crucial property: the arcs were simplified in place via topojson-simplify and never rebuilt, so both levels share arc indices 1:1 and carry identical properties in identical order.

Boundaries renders them as two L.geoJSON layers (islands and waters, split on Config.boundaries.typeProperty) plus a L.layerGroup of flag markers. Level selection is driven by zoom against Config.boundaries.simplifyZoomThreshold (9), and rebuildForZoom() short-circuits unless the level actually crosses the threshold — so ordinary zooming costs nothing. When it does rebuild, it captures each layer's current on/off state first and restores it, so a user who turned Waters off in the legend doesn't have it reappear on zoom.

Two details here are better than they needed to be:

Flag anchoring. flagLatLng() doesn't use the bbox centre, because for a MultiPolygon archipelago that lands in open water. Instead it picks the largest sub-polygon by ring area (GeoMath.largestPolygon), computes that ring's centroid, and — if the centroid falls outside the ring, as it does for concave shapes — falls back to the nearest ring vertex, then to the bbox centre only as a last resort so hover feedback is never silently lost.

Water/island pairing. A territory's water polygon has a different NAME_0 ("Dominican Waters") than its island ("Dominica") but shares GID_0. build() precomputes anchorByGid0 before Leaflet invokes onEachFeature, so water tooltips render at exactly the island's flag position. geo-index.js uses the same key and comments on why SOVEREIGN was rejected: Guadeloupe and Martinique both have SOVEREIGN: "France", which would wrongly merge two distinct islands.

6.3 Markers

One Leaflet marker is created per feature at init and never destroyed. Visibility is addTo / removeLayer against the pre-built instances; icons are L.divIcon with inline SVG from Shapes.

The adaptive colour mode is a nice piece of product thinking. highlightByRole starts true — markers are coloured by creole role, the dimension the archive is actually about. computeHighlightByRole() scans for how many distinct roles survive the current filters, bailing early once it finds a second. If filtering collapses to a single role, role has nothing left to distinguish, so refreshIconMode() restyles every marker to its category colour instead. Same icon geometry either way; only the fill changes. It only restyles when the mode actually flips.

visible() caches the hasLayer filter and invalidates in applyVisibility() — worth noting because the hit-testers call it on every selection.

6.4 Selection: the most sophisticated subsystem

Arming a tool (arm()) does considerably more than set a flag. It disables Leaflet's dragging, doubleClickZoom, tap, and boxZoom — the last with a comment explaining that Shift+drag is Leaflet's native box-zoom, which would otherwise fight the Shift-as-union modifier. It sets touch-action: none both via CSS class and inline, with a comment on why: touch-action is resolved before pointer events dispatch, so if the class rule loses a specificity battle or applies a tick late, the first pointermove arrives as a pointercancel instead.

Hit testing correctly uses two different coordinate spaces:

  • Screen space for drawn shapes. containerPoint(marker) projects each visible marker to container pixels and tests against the pixel-space rectangle/ellipse/polygon. This is right: the user drew in pixels, so an ellipse should be an ellipse on screen, not a distorted geodesic region.
  • Geographic space for object select. GeoMath.pointInGeometry(lng, lat, geometry) ray-casts the marker's lat/lng against the boundary polygon's rings, with holes handled (rings[0] outer, the rest subtractive). An extent mode does a cheap bbox test instead, toggled by a dedicated pair of toolbar buttons.

GeoMath's header records that this ray-casting was previously copy-pasted across three modules and has been consolidated — the kind of note that saves the next engineer from re-forking it.

Hits flow to SelectionState.applyHits(), which delegates combination to SelectionAlgebra — four one-line set operations in a lookup table, with no state and no DOM. That separation is what makes the modifier-key override cheap: onKeyDown records the current mode, switches to the modifier's mode, and onKeyUp restores it. A single override is tracked at a time (mirroring the single-select mode buttons), evt.repeat is guarded, editable targets are excluded, and a window blur listener restores the mode if focus leaves while a modifier is held — otherwise alt-tabbing would leave the override permanently stuck.

The middle-click pan deserves specific mention as the most advanced piece of Leaflet integration here. Because arming disables dragging entirely, middle-click panning is hand-rolled: on middle pointerdown it snapshots the map pane's transform and pixel position (via map._getMapPanePos(), with a regex fallback parsing translate3d if that private method disappears), then accumulates deltas and writes translate3d directly to the pane inside a requestAnimationFrame. On release it restores the original transform first so Leaflet's internal position is consistent, then commits the real offset with a single panBy({animate: false}) — producing exactly one move/moveend pair instead of hundreds. That last point is not incidental: moveend is what drives viewport:changed → URL writes.

6.5 The three feedback loops

Filter loop Legend checkbox / analytics bar click / timeline brush / year slider → FilterState setter → touch(group) → filters:changed → Markers.refreshIconMode() + applyVisibility(), AnalyticsPanel.render(), Legend.syncCheckedState(), StateSyncManager (debounced 300 ms).
Selection loop Pointer gesture → SelectionToolbar → GeoMath hit test → SelectionState.applyHits() → SelectionAlgebra.combine() → selection:changed → marker highlight classes, results-list reconciliation, analytics rescope, URL push.
Viewport loop Leaflet moveend → viewport:changed → ViewportQuery.featuresInView() rescan → results list and analytics update (debounced 150 ms for analytics), URL replace (debounced 300 ms).

ViewportQuery is the single implementation behind all three "which features are in view" questions, parameterized by respectFilters: "none" | "active" | "ignoreYear". Its header records that three modules previously each scanned the dataset independently. The "ignoreYear" mode exists for one specific reason: the decade histogram must show the full distribution for context, because if it respected the year filter every out-of-range decade would read as zero and the user would have nothing to drag back toward.

6.6 Two pieces of unusually careful product logic

Hidden-record attribution. The analytics panel shows "N records hidden by the X filter" for each of four filters. A record failing three filters at once must be attributed to exactly one, or the four notices won't sum to the real hidden total. FilterState.classifyHiddenReason() solves this by tracking, via a monotonic touchCounter, which filter group the user touched least recently among those currently blocking the record — the reasoning being that the filter you're actively dragging is already the obvious cause, so the notice should surface the one that's easy to overlook. The comment records that a previous approach (diffing against a scope with one filter lifted) silently undercounted, and that ties fall back to a deterministic seed order. setAllVisible() deliberately does not touch the counter, because a blanket reset isn't the user focusing on one filter.

Bidirectional timeline. The analytics histogram and the footer slider are the same filter viewed twice. Brushing the histogram calls TimeSlider.setRange(), which drives noUiSlider programmatically; noUiSlider's own update handler then notifies FilterState. Control flows one way and the state converges — no two-way binding, no reconciliation.

6.7 UI synchronization quirks

Panels coordinate through the bus in ways worth knowing before touching them. createCollapsible broadcasts panel:collapseChanged with a name; Legend and Results each listen for the other and mutually collapse on desktop, because their layouts overlap when both are open. Results carries a hasArmedOnce latch so the first time any tool is armed it switches from "Visible in view" to "Selection" mode — once only, so it doesn't fight the user afterward. Search sets searchActive in Markers, which is the only path that hides non-selected markers; every other selection source highlights in place.

This is the most implicitly-coupled area of the codebase. results-panel.js alone carries seven bus subscriptions with interlocking collapse rules.

Two design notes visible in this trace. First, applyHits receives indices, not markers — the map layer converts to domain identity at the boundary, so SelectionState never touches Leaflet. Second, both ResultsViewState.selectAll() and Searchbar.runSearch() need to replace rather than combine, so both save the mode, force "new", apply, and restore — a small repeated idiom that would be cleaner as an explicit SelectionState.replaceWith().

The URL write policy is a considered piece of design. pushState (immediate, new history entry) for discrete changes — basemap, overlay, selection, sort. Debounced replaceState (300 ms, coalesced) for continuous ones — viewport and filters. filters:changed lands in the debounced bucket even though a checkbox click is discrete, and the code explains the tradeoff: it's the same event as every tick of a slider drag, so treating it as discrete would flood pushState. The cost is ~300 ms of URL staleness after a checkbox click, which is imperceptible. suppressWrites guards the apply path so restoring a state doesn't re-serialize it.

Important Components and Responsibilities

What an engineer must understand first
config.js Genuinely centralized. Tile URL builder, initial view, both overlay definitions with their georeferenced bounds, boundary styling, the simplification threshold, debounce timings, the polygon double-tap window. The boundary block even documents how to discover the right typeProperty for a different data source (console.table(BoundaryData.getFeatures().map(f => f.properties))).
event-bus.js 12 lines. Understand it in 30 seconds and you understand how the app is wired.
filter-state.js The most load-bearing state module. Owns four filter dimensions and a single parameterized predicate, isFeatureVisibleIgnoring(props, {ignoreYear}), from which both public predicates derive so they can't drift apart. Encodes a real domain rule: "others" and null collapse into one bucket for both category and author type, and always pass — so "Other / Unknown" records stay visible no matter which specific type is being focused.
state-sync-schema.js The purest module and the most reusable. sanitizeState(partial, fallback, bounds) never throws and always returns a fully valid state, validating every field against live bounds (zoom vs. maxZoom, IDs vs. actual layer IDs, years vs. dataset extent, selection indices vs. featureCount). serializeState omits anything equal to default, so a pristine view has a clean URL. This module is the foundation for both future modes.
state-sync-manager.js The URL bridge, and the file to read first. Its 40-line integration-notes appendix is the best documentation in the repo: it explains why the app's state shape refused to fit a generic model, records the index-identity risk, notes that Basemaps.setOverlay() toggles rather than sets (so clearing means re-toggling the active ID), and states that localStorage was intentionally dropped. It also owns the private applyStateToApp() — the function both future modes need.
panel-behaviors.js Extracts the collapse state machine and header mounting shared by three panels. Its NARROW_VIEWPORT_QUERY = "(max-width: 30rem)" constant carries an honest warning that CSS custom properties can't be read inside a media query condition, so this is hand-synced with responsive.css.
geo-math.js / selection-algebra.js Pure, dependency-free, and the two modules most obviously ready for unit tests that don't exist.

Key Engineering and Design Decisions

Marked C confirmed I inferred U undeterminable

9.1 Vanilla ES modules with no build step

Evidence C
No package.json, no lockfile, no config for any tool. <script type="module"> with relative .js imports. Vendored libraries as classic scripts assigning globals. GitHub Pages hosting.
Reasoning I
Push-to-deploy with zero pipeline; the deployed artifact is the source, so devtools show real code with real names; no toolchain to age or break. For a single-developer prototype on Pages, correct.
Tradeoffs
No minification or tree-shaking. 36 sequential module requests plus 15 sequential CSS @imports on cold load. No lint or type checking — nothing catches a typo'd event name.
Future
Adding esbuild or Vite later is nearly free (this is standard ESM). Do it when cold-load latency or team size makes it worthwhile, not before.

9.2 Leaflet rather than MapLibre / Mapbox GL

Evidence C
Leaflet 1.9.4 from CDN. All tile sources are raster (CARTO PNGs + local PNG pyramids). Markers are L.divIcon with inline SVG. Marker selection is iconEl.classList.toggle("is-selected-marker", …).
Reasoning I
Two decisive fits. The data is raster — the historical overlays are pre-rendered PNG pyramids, so a vector-first engine would bring no benefit. And divIcon markers are real DOM nodes, so the entire CSS design system applies to them directly; the same is not true of GL-rendered symbols, where selection styling means shader-level feature-state management.
Tradeoffs
DOM markers cap out in the low thousands. No 3D, no vector styling, no smooth fractional zoom.
Future
The ceiling is a real dataset-size limit (§15). Mitigations in order of cost: canvas renderer for boundaries → marker clustering → GL engine. Only the last is a rewrite, and only a very large dataset would justify it.

9.3 Static HTML shells filled by JS

Evidence C
map.html declares every panel skeleton with stable IDs; basemaps.js and legend-panel.js both comment that markup lives in HTML and "only the per-layer buttons are data-driven from Config."
Reasoning I
Panels are present and styled before JS runs — no flash of unstyled or missing chrome. CSS is authored against markup that actually exists. JS stays behavior-only.
Tradeoffs
~40 getElementById calls against literal IDs. This is exactly what makes a second, independently-instantiated map hard (§13).

9.4 Array indices as record identity

Evidence C
SelectionState holds Set<number>. sanitizeSelection validates against bounds.featureCount. The URL carries sel=3,7,12. ArchiveData features have no id property.
Reasoning I
With a hardcoded 25-record literal, index is identity, and it produces short URLs.
Tradeoffs
The code names this itself: indices "are only valid as long as the dataset itself doesn't change shape. If ArchiveData ever becomes dynamic (loaded/paginated/re-ordered), this needs a real id field before it's safe to persist."
Future
This is the single highest-priority change in the repository. Any shared link, saved story, or comparison scenario silently breaks the moment a record is inserted, removed, or reordered. Adding an id field costs an afternoon now and gets more expensive with every artifact that references indices.

9.5 Federated state singletons over a central store

Evidence C
Five independent state owners, no store module, coordination purely by event.
Reasoning I
Each concern's invariants live with its data; adding a filter dimension touches one file. Avoids the boilerplate of a store for an app whose state is genuinely small.
Tradeoffs
No single place to snapshot, diff, or time-travel — which is why StateSyncManager has to reach into five modules to assemble a state object. Cross-cutting operations (like "apply this whole state") are awkward, and the current implementation shows it: applyStateToApp calls 17 individual filter setters, each emitting filters:changed, each triggering a full analytics rebuild.
Future
Don't add a store library. Do add a batched apply path per state owner (§14).

9.6 CSS custom properties as the colour source of truth

Evidence C
All category/author/role colours defined in root.css; Theme reads them via getComputedStyle at module init; Shapes receives colours as arguments.
Reasoning I
One definition serves CSS rules, SVG marker fills, legend swatches, and analytics bars — no duplicated hex values.
Tradeoffs
Read once at import. Today that's safe, because the semantic colours live on :root and only surface colours vary by [data-theme]. But it silently constrains any future per-theme or user-customizable palette.

9.7 Dual-resolution boundary simplification

Evidence C
BoundariesTopoFine (~19% of points) / BoundariesTopoCoarse (~7%), arcs simplified in place so indices match 1:1; levelForZoom() at threshold 9; rebuildForZoom() no-ops unless the level changes.
Reasoning C
The config comments state it: below the threshold more geometry is visible at once, so redraw cost is worst exactly where the extra detail is least perceptible.
Tradeoffs
Two copies of the topology in one 370 KB file, parsed on load. A rebuild at the threshold discards and recreates both L.geoJSON layers plus all flag markers.

9.8 Fidelity-mocked export

Evidence C
13 formats with per-format hints; the confirm handler is close().
Reasoning I
The design question being tested is which formats matter and how the chooser should feel, not whether a Shapefile encoder works. Building real encoders for 13 formats would consume the entire prototype budget and answer nothing about the product.
Future
Formats split cleanly. Data formats (CSV/JSON/GeoJSON) are trivial client-side from the selected features. Map formats (PNG/PDF) need canvas rasterization. GIS binaries (SHP/GPKG/FGB) realistically need a server. The format list is itself a product requirement document — it should inform the backend scope when one exists.

9.9 Undeterminable U

Whether the historical overlays are licensed for redistribution (attributed to Old Maps Online, but no LICENSE file exists); the provenance and licence of the boundary topology (properties are GADM-shaped, but nothing states it); whether the single squashed commit hides meaningful history; whether the 25 records are representative of the eventual corpus's shape or scale.

What Works Particularly Well for a Prototype

Six strengths worth preserving
  • Configuration discipline. Config is genuinely the only place tunables live, and it's honoured. Retargeting the prototype to a different archipelago is plausibly a config edit plus new tile pyramids.
  • Comment quality. Comments explain why, and several record rejected alternatives with the reason for rejection — classifyHiddenReason's undercounting problem, GID_0 vs. SOVEREIGN, why touch-action is set twice, why boxZoom must be disabled. state-sync-manager.js's integration appendix is close to an ADR. This is the project's most valuable and most fragile asset: it will decay silently unless maintained.
  • Real interaction depth. Boolean selection algebra with modifier keys, unified pointer input, hand-rolled middle-click panning, geometry-vs-extent object selection, brushable histogram. These are the hard parts of this kind of tool, and they're done rather than sketched.
  • Naming correspondence. #legend-panel ↔ legend-panel.js ↔ legend-panel.css holds across every panel. Finding the code for a piece of UI takes no search.
  • Accessibility as a default rather than a pass. Keyboard-operable markers, ARIA state maintained through every toggle, focus return on Escape, deliberate omission of a default aria-expanded in mountHeader so no incorrect value ever flashes in the DOM.
  • Genuinely reused abstractions. GeoMath, ViewportQuery, and panel-behaviors were each extracted from three duplicated call sites, and each file says so.
  • Correct rendering strategy where it counts. SelectionResults.render() does keyed reconciliation — it removes rows whose indices vanished, then walks the desired order reusing existing rows and only moving what's out of place. No teardown, no rebuild. This is the right pattern, and it makes the contrast with AnalyticsPanel (§15) instructive rather than accidental.

Current Architectural Limitations

Ordered by how soon they will actually bite
  1. Index-based identity (§9.4). Blocks real data, saved stories, and shareable comparison states. Fix first.
  2. MapCore as a construction-time singleton. ~15 modules import it directly. Blocks comparison mode entirely.
  3. No batched state application. Restoring a state emits filters:changed 17 times; each rebuilds the analytics panel. Invisible at 25 records; disqualifying for story-step transitions.
  4. Panel DOM binding by global ID. Prevents two instances of any panel.
  5. Unthrottled filters:changed → full analytics teardown. The dominant performance risk (§15).
  6. No test coverage. state-sync-schema.js, geo-math.js, and selection-algebra.js are pure and explicitly written to be testable. Nothing tests them.
  7. Implicit panel coupling. Seven interlocking bus subscriptions in results-panel.js; adding a mode means reasoning about all of them.
  8. Silent 200-index URL cap. A lasso over a dense region produces a link that quietly drops the selection. Acknowledged in code, no user-facing warning.
  9. DOM markers, no clustering, SVG boundary renderer. A hard ceiling in the low thousands of records.
  10. Dead vendor duplicates under misleading names (§5).
12

Future Mode: Data Story

Most of it already exists

12.1 The central insight

Most of a story engine already exists. StateSyncManager defines a canonical, serializable, fully-validated application state (sanitizeState), a function to read it from the live app (readCurrentAppState), and a function to apply it back (applyStateToApp). A story step is one of those state objects plus narrative text.

This means Data Story Mode requires no new state model, no rendering changes, and no changes to any panel. Every panel already re-renders in response to the same events that applyStateToApp triggers. The work is extraction, sequencing, and a narrative UI.

12.2 Recommended architecture

StoryDefinition  (declarative data — no code)
      ↓
StoryStep  { narrative, statePatch, transition, annotations }
      ↓
StoryController  (index, next/prev, merge patch over baseline)
      ↓
StateApplier.apply(state, {animate})     ← extracted from StateSyncManager
      ↓
existing EventBus events → existing panels, markers, boundaries (UNCHANGED)

Steps should carry partial states merged over the previous step's resolved state, not full states. A step that only says "now zoom to Martinique" shouldn't have to restate every filter, and authors shouldn't have to keep 10 fields in sync across 12 steps.

const story = {
  id: "creole-emergence",
  title: "The Emergence of Written Creole",
  baseline: { /* optional full state; defaults to Config defaults */ },
  steps: [
    {
      id: "overview",
      narrative: { title: "A Scattered Archive",
                   body: "Across the Lesser Antilles, 25 surviving documents…" },
      state: { center: [15.5, -61.2], zoom: 8, yearRange: [1648, 1861] },
      transition: { map: "flyTo", durationMs: 1200 }
    },
    {
      id: "early-clergy",
      narrative: { title: "The Missionary Record", body: "…" },
      state: { yearRange: [1648, 1720], activeAuthorTypes: ["clergy"] },
      transition: { map: "flyTo", durationMs: 900 },
      annotations: [{ type: "marker-emphasis", records: ["rec-007", "rec-014"] }]
    },
    {
      id: "martinique-focus",
      narrative: { title: "Martinique", body: "…" },
      state: { center: [14.64, -61.02], zoom: 10 },
      annotations: [{ type: "region-highlight", boundaryGid0: "MTQ" }],
      transition: { map: "flyTo", durationMs: 1000 }
    }
  ]
}

12.3 What to build

  1. Extract StateApplier (~40 lines, mechanical). Lift applyStateToApp out of StateSyncManager into state/state-applier.js and add an options argument: 
    export function applyState(next, {animate = false} = {}) {
  animate ? MapCore.map.flyTo(next.center, next.zoom, {duration: …})
          : MapCore.map.setView(next.center, next.zoom, {animate: false})
  // …everything else applies instantly; only the map animates
}
    StateSyncManager then calls it with {animate: false} and behaves identically. StoryController calls it with {animate: true}. Filters and selection apply instantly during the fly-to, which is correct — animating a filter change means animating markers in and out, which reads as noise.
  2. Add FilterState.applySnapshot({yearRange, categories, authorTypes, creoleRoles}) — one notify() instead of 17. This is a prerequisite, not a nice-to-have. Without it every story transition triggers 17 full analytics rebuilds mid-animation.
  3. StoryController — owns currentStoryId and currentStepIndex, resolves each step by merging its patch over the previous resolved state, calls sanitizeState (free validation), then StateApplier. Emits story:stepChanged.
  4. Story URL scheme. Extend state-sync-schema.js with story and step keys. When a story is active, serialize ?story=creole-emergence&step=3 instead of the full state — the story definition already encodes the state, and Back/Forward then steps through the narrative, which is exactly the desired behaviour.
  5. Story panel — narrative text, progress, prev/next, exit. Reuse panel-behaviors.js for the shell. Suppress or lock the selection toolbar while a story is active.
  6. Annotation layer — the one genuinely new capability. Use a dedicated L.layerGroup, rebuilt per step from declarative step data. Do not overload SelectionState: story emphasis and user selection are different concepts with different lifetimes, and conflating them will produce bugs where exiting a story leaves a phantom selection. For region highlights, reuse the existing GID_0 lookups in geo-index.js.

12.4 What stays untouched

Markers, boundaries, basemaps, legend, analytics, results, search, time slider, popups, geo-math, selection-algebra, viewport-query, all CSS. This is the strongest argument for the approach: the entire feature reuses the existing rendering pipeline through the existing event vocabulary.

12.5 Prerequisites and risks

Blocking
Stable record IDs. A story step that emphasizes records must not reference [7, 14].
Blocking
applySnapshot batching.
Risk
AnalyticsPanel's full teardown per filters:changed will visibly stutter mid-fly-to. Batching mostly solves it; adding a "quiet" mode that defers analytics rendering until a transition settles is the belt-and-braces version.
Non-risk
Authoring. Stories are plain data and can live as a JS module exactly like ArchiveData does today.
Estimate: the smallest honest version is a few days of work, most of it in the narrative UI rather than the architecture. Note that StateSyncManager.getShareableUrl() plus readCurrentAppState() already give you "capture the current view as a step" nearly for free.
13

Future Mode: Side-by-Side Comparison

A real refactor — bigger than Data Story

13.1 The constraint

map-core.js calls L.map("map") at module evaluation time. Roughly fifteen modules import MapCore and use MapCore.map or MapCore.getContainer() directly. FilterState, SelectionState, Markers, Boundaries, and ViewportQuery are all IIFE singletons instantiated on import. Panels bind to global DOM IDs.

There is no shortcut around this. Comparison mode is a real refactor — meaningfully larger than Data Story Mode — and it should not be attempted first.

13.2 Choosing the comparison model

Model Verdict
Swipe / curtain over one map Cheapest, but can only compare tile layers. Cannot show two different filter states, which is the comparison this dataset actually supports (period × category × author type). Rejected.
One map, two marker sets, differential styling No refactor needed, but conflates two states in one viewport; illegible past a handful of records. Rejected as the primary model — though it is exactly right for the difference overlay (§13.4).
Two map instances, synced viewport, independent filter/selection state, shared data Honest, reuses every rendering module wholesale, supports every comparison axis the data offers. Recommended.

13.3 The minimum refactor

  1. MapCore becomes a factory. createMapContext(containerEl) returns {id, map, bus, filterState, selectionState, markers, boundaries, viewportQuery}. Keep a module-level defaultContext created against #map, and have the current single-map page pass it through — so the existing page changes in one place, not fifteen.
  2. EventBus becomes instantiable. It's twelve lines: export createEventBus() alongside the existing default instance. Per-context buses are what prevent left-pane filter changes from leaking into the right pane, and they cost nothing.
  3. Convert the state and map modules to factories. FilterState, SelectionState, ResultsViewState, Markers, Boundaries, ViewportQuery become createFilterState(ctx) etc. This is mechanical: each already closes over private state, none writes to another module's internals, and their dependencies are already explicit imports. Config, Theme, GeoMath, SelectionAlgebra, Shapes, ArchiveData, BoundaryData, and GeoIndex are stateless or read-only and stay singletons — which is what keeps this from doubling everything.
  4. Panels take (ctx, rootEl). Replace document.getElementById("x") with rootEl.querySelector(".x"). Mechanical but touches every panel; this is the bulk of the work.
  5. ComparisonController: 
    const ComparisonController = (() => {
  let left, right
  let linkViewport = true
  let linkFilters  = true
  let isEchoing = false          // same re-entrancy guard as suppressWrites

  function mirrorViewport(from, to) {
    from.bus.on("viewport:changed", ({center, zoom}) => {
      if (!linkViewport || isEchoing) return
      isEchoing = true
      to.map.setView(center, zoom, {animate: false})
      isEchoing = false
    })
  }
  // filters mirror the same way, via applySnapshot (§12.3)
})()
    The isEchoing guard is the same pattern StateSyncManager already uses for suppressWrites — a known-good idiom in this codebase rather than a new one.
  6. Filters default to linked, with an explicit per-group unlink. The compelling comparisons are "same filters, two places" and "same place, two periods" — both need most dimensions linked and one free. Defaulting to fully independent forces the user to re-specify everything twice to get to the interesting state.

13.4 Difference display

Compute the set difference of visible feature indices between contexts and express it as marker styling, not a new layer — .is-only-left / .is-only-right / .is-both classes toggled on the existing divIcon elements, exactly as is-selected-marker already works. It reuses the whole marker pipeline and costs one classList.toggle per marker.

Numeric differences belong in a third, shared analytics strip between the panes ("Left: 12 records · Right: 7 · 4 in both"). AnalyticsPanel's counting functions can be reused directly if the counting logic is separated from the rendering — which it currently is not, and which is worth doing as part of the analytics cleanup recommended in §15 anyway.

13.5 Responsive behaviour

Do not render two maps below the 30 rem breakpoint. Two Leaflet instances on a phone means two tile pyramids in flight, two marker DOM trees, and two SVG boundary layers. Instead, render one map with a tab or toggle between the two states, reusing the existing bottom-sheet panel layout. The A/B toggle preserves the comparison intent; simultaneity is a desktop affordance.

13.6 Performance

Two maps roughly double tile requests, marker DOM nodes, and boundary SVG paths. Three mitigations already exist or are cheap:

  • Boundary geometry decoding is already shared. BoundaryData caches decoded features per level in a module-level Map, and it stays a singleton — so only rendering doubles, not parsing. This is a real, pre-existing advantage.
  • Tiles are cached by the browser across both instances, including the 211 MB local pyramids.
  • Boundaries should move to L.canvas() before comparison ships. Two SVG boundary layers is the most likely rendering bottleneck, and this is a one-line renderer option.

13.7 Sequence

  1. Stable record IDs (§9.4) — needed to share a comparison state at all
  2. FilterState.applySnapshot() — needed for linked filters
  3. createEventBus() — trivial, unblocks everything else
  4. createMapContext() with a default context — single-map page unaffected
  5. Convert state/map modules to factories
  6. Scope panels to (ctx, rootEl) — the bulk
  7. Split layout + ComparisonController + viewport sync
  8. Difference styling + shared diff strip
  9. Mobile A/B fallback

Steps 1–3 are worth doing regardless of whether comparison mode ever ships.

Performance and Scalability

Excellent today; nine findings for tomorrow
Current runtime performance is excellent — 25 markers, ~40 boundary polygons, and a well-behaved tile pipeline. Every finding below is about what happens as the dataset grows or the future modes land.
HIGH · 1

AnalyticsPanel.render() full teardown, driven by unthrottled filters:changed

Where
analytics-panel.js render(); time-slider-footer.js on("update").
Why it matters
render() rebuilds all six sections via innerHTML, re-attaching roughly twenty event listeners, and internally performs three full dataset scans (featuresInView twice — once for scope, once for the ignore-year timeline scope — plus hiddenCounts), with a GeoIndex.islandFor() lookup per record. It is subscribed to filters:changed without debouncing, and noUiSlider's update event fires continuously during a drag. Dragging the year slider therefore triggers a complete teardown-and-rebuild of six DOM sections, plus three dataset scans, per frame.
The tell
Map movement is debounced at 150 ms in the same init(). Filter changes are not, despite being the higher-frequency source.
Impact
Negligible at n=25. At n=10,000 a slider drag becomes unusable; during story-mode transitions it will visibly stutter mid-animation.
Fix
(a) debounce the filter-driven path as the map path already is; (b) separate the counting functions from the rendering functions so counts can be computed once and reused — this also makes them reusable for comparison mode's diff strip; (c) adopt SelectionResults' keyed reconciliation for the bar rows instead of innerHTML teardown. The correct pattern already exists in this codebase, twelve files away.
HIGH · 2

Markers.applyVisibility() on every filter and selection tick

Where
markers.js.
Why
Iterates all markers calling addTo / removeLayer, each touching Leaflet's DOM. Runs on every filters:changed and every selection:changed — again, per slider frame.
Fix
Track the previously-visible set and diff, so only markers whose visibility actually changed are touched. Most slider ticks change zero or a handful.
HIGH · 3

Marker rendering has no scaling strategy

Where
markers.js (one DOM divIcon per feature), boundaries.js (default SVG renderer).
Why
DOM markers cap out in the low thousands; two simultaneous SVG boundary layers (comparison mode) is the most likely rendering bottleneck.
Fix, in order of cost
L.canvas() renderer for boundaries (one line, do it before comparison mode); marker clustering when the dataset warrants it; viewport-windowed marker creation as a last resort.
MEDIUM · 4

Linear scans in GeoIndex, called per render

Where
flagForIsland() does .find() across all boundary features; boundsForIsland() filters all indexed boundaries. Both are called once per island row, on every analytics render.
Fix
Build flagByName and boundsByName lookup maps once, alongside the existing gid0ByName / islandNameByGid0 maps that already use exactly this pattern.
MEDIUM · 5

ViewportQuery is an unindexed full scan

Where
featuresInView() iterates every feature testing bounds.contains.
Why
Fine at n=25; O(n) per call, called up to three times per analytics render, plus once per results render, plus on every moveend.
Fix
Not yet. When the dataset grows, add a simple grid index or an R-tree. The single-implementation consolidation already done here makes that a one-file change.
MEDIUM · 6

Boundary rebuild at the zoom threshold

Where
rebuildForZoom() discards and recreates both L.geoJSON layers plus every flag marker, re-running flagLatLng() (largest-polygon + centroid + point-in-polygon) for each island.
Why
Correctly gated to fire only when the level actually changes, so it's rare. But a user oscillating across zoom 9 pays it repeatedly.
Fix
Cache computed anchors by GID_0 across rebuilds — they don't depend on simplification level in any way the user can perceive.
MEDIUM · 7

Silent 200-index URL truncation

Where
MAX_SELECTION_IN_URL in state-sync-schema.js.
Why
A lasso over a dense region produces a shareable link that quietly drops the selection. Acknowledged in the code's own notes; no user-facing warning.
Fix
Surface it in the UI, or move to ID-range compression once records have IDs.
LOW · 8

Panel event subscriptions are never released

Where
Every panel's init(). Only StateSyncManager collects unsubscribers.
Why
No leak today, because nothing is ever destroyed. Becomes a genuine leak the moment comparison-mode contexts can be created and torn down.
Fix
Address as part of the context-factory refactor, not before.
LOW · 9

Repository weight

Where
211 MB of raster tiles in git, contributing most of the 415 MB clone.
Fix
Fine for a self-contained prototype; consider Git LFS or a CDN if history grows.

Maintainability and Technical Debt

What's strong, and what will hurt first

Strong today

Configuration centralization; the three-way HTML/CSS/JS naming correspondence; genuinely extracted shared abstractions (GeoMath, ViewportQuery, panel-behaviors), each documenting the duplication it replaced; pure modules cleanly separated from DOM modules; the comment culture.

The real debt, in the order it will hurt

  1. Index identity. Every day this persists, more artifacts (shared links, future stories, future comparison states) accumulate against an unstable key. Fix now.
  2. Implicit panel coupling. results-panel.js carries seven bus subscriptions with interlocking rules — hasArmedOnce, mode auto-switching on tool arm, mutual collapse with the legend, search-driven mode changes. Adding a mode requires reasoning about all of them simultaneously, and there's no test to catch a regression. This is the most likely source of subtle bugs when story mode lands. Consider consolidating the panel's mode transitions into an explicit small state machine before adding a fourth mode to it.
  3. Zero test coverage on pure logic. sanitizeState alone has a dozen validation branches. geo-math's ray-casting and hole handling is exactly the kind of code where an off-by-one hides for months. These modules were written to be testable — state-sync-schema.js says so in its header. Add the tests before the refactors in §13, not after; they're the safety net for the mechanical conversion.
  4. Analytics rendering pattern. The one place where teardown-and-rebuild was used instead of the reconciliation pattern used elsewhere. It's also the module both future modes will lean on hardest.
  5. Dead vendor duplicates. Trivial to fix, actively misleading until fixed.
  6. Documented hand-synced values. NARROW_VIEWPORT_QUERY must match responsive.css; Theme reads CSS vars once at init. Both are correct today and both are commented, which is the right handling in a no-build project — but both are silent-breakage risks.
  7. window.toggleWindowPopup. A global function referenced from an inline onclick inside generated popup HTML — the one place the otherwise-clean module boundaries are bypassed. Fine now; convert to a delegated listener when the popup gains a second action.

Final Expert Assessment

Where this stands, and what's next
Prototype quality
Excellent. This is well beyond a proof of concept. The interaction model — boolean spatial selection with modifier keys, dual-space hit testing, live analytics rescoping, shareable deep-linked state — is the genuinely hard part of a tool like this, and it is finished, not sketched. The mocked layers (data, export, source viewer) are exactly the layers a prototype should mock, and the boundaries between real and simulated are clean enough to describe in a paragraph.
Architecture
High, with two specific structural constraints. The layering is real and enforced by import direction. Pure logic is genuinely pure. The event bus keeps 36 modules decoupled at a cost of twelve lines. Federated state is the right call at this scale. The two constraints — index identity and the construction-time map singleton — are both consequences of reasonable prototype decisions, and the codebase names the first one itself.
Maintainability
Above average for any codebase, unusually high for a prototype. The comment culture is the standout: comments that explain reasoning and record rejected alternatives are rare in production code, let alone prototypes. Preserve this deliberately — it is the asset most likely to decay silently under time pressure.
Story Mode readiness
High. The state model, serialization, validation, and application logic already exist. The work is extraction plus a narrative UI. Two small prerequisites (stable IDs, batched filter apply). No panel changes, no rendering changes, no structural refactor. This should be the next feature.
Comparison readiness
Moderate, and gated on a real refactor. Every module that needs to become multi-instance is already a closure over private state with explicit dependencies, which makes the conversion mechanical rather than architectural — but it touches roughly fifteen files.
